# 前端开发：先做可见的 demo，再写正式代码

## 为什么要有这条

写前端最容易翻车的顺序是：**先写代码 → 写完给用户看 → 他说不是这个意思 → 推倒重来**。

界面是**看**出来的，不是描述出来的。用户说"做个好看的后台"，你按自己的理解写 800 行，
他看到的可能完全不是他脑子里的那个东西 —— 而这个偏差**在写代码之前就能发现**。

所以：**先在画布里把界面摆出来给他看，确认之后，再写正式代码。**
画布里的东西是**活的、可点、可改**的，用户能直接说出"这个按钮再大一点"，
而不是等到代码写完再返工。

## 什么时候用

**用**：
- 新做一个页面 / 界面 / 组件 / 落地页 / 后台 / 表单 / 列表 / 卡片
- 用户说"帮我设计""做个好看的""改一下界面"
- 需求里出现视觉描述（配色、圆角、间距、布局）

**不用**：
- 纯后端 / CLI / 数据处理 / 脚本
- 用户已经给了明确的设计稿或 Figma 链接（照着实现即可）
- 改一行文案、修一个 bug

**判据一句话**：**这次交付的东西，用户会"看见"吗？** 会 —— 就先做 demo。

## 怎么做

### 1. 先问清楚，别急着画

一次问完：**给谁用**（用户/管理员/访客）、**干什么用**（核心动作是什么）、
**什么调性**（专业/活泼/极简）、**有没有参考**（喜欢的网站/已有的设计系统）。

**别问**："你喜欢什么颜色"这种 —— 用户答不上来。**给选项**：
"我准备做 A 这种紧凑的表格风格，还是 B 这种卡片风格？"

### 2. 先搭一个最小 HTML 页面

**不要**在这一步引入框架、构建、依赖。一个 `.html` 文件就够 ——
后面才决定用什么技术实现。

放哪里：项目的 `demo/` 或 `design/` 目录（**别直接写进 `src/`**，
demo 是给人看的草稿，不是正式代码）。

### 3. 把它挂进画布

启动画布（`http://127.0.0.1:19387/canvas/`），`＋ 添加画板` 填 demo 页面的路径。

**确认它真的挂上了** —— 调一次 `canvas_status`，看返回里的 `projectRoot`
和画板列表对不对。挂不上最常见的原因是 `projectRoot` 没配或路径不存在。

### 4. 在画布里调，而不是改代码

优先用**画布本身**的交互（点选、拖拽、属性面板）—— 它走的是和人类相同的写回管道，
改一下源码就变一下，用户能立刻看到。

需要批量或精确改时用工具：

| 工具 | 什么时候用 |
|---|---|
| `canvas_status` | 开始前确认画布接上了、项目栈是什么 |
| `canvas_locate` | 用户说了个元素（"那个蓝色按钮"），但你不知道它在源码哪一行 |
| `canvas_style` | 改样式。和人类拖属性面板走**同一条写回管道** |
| `canvas_undo` / `canvas_redo` | 用户说"还是上一版好" |
| `canvas_pending` | 配置成先预览时，落盘或丢弃待确认的改动 |

### 5. 拿给用户看，让他说

**这一步不能跳。** 说清楚三件事：
1. **现在长什么样**（截图 / 让他刷新看）
2. **我做了哪些取舍**（"表格用了斑马纹，因为列多"）
3. **哪里还不确定**（"侧边栏要不要能收起？"）

**等他确认**，再动正式代码。他要改就直接在画布里改 —— 比描述快得多。

### 6. 确认之后，才写正式代码

这时才决定技术栈、拆组件、接数据。**demo 里的样式可以直接搬** ——
它是真实可跑的 HTML/CSS，不是假图。

## 反模式

| ❌ | ✅ |
|---|---|
| 上来就 `npm create vite` 然后写 800 行 | 先一个 HTML 把样子摆出来 |
| 口头描述"我会做一个卡片列表" | 直接做出来给他看 |
| 用户说"按钮大一点"，你去猜 px 值 | 在画布里拖一下，他当场看到 |
| 把 demo 直接写进 `src/` | 放 `demo/`，确认后再搬进去 |
| 用户没确认就接着写下一屏 | 一屏一确认，改起来才便宜 |

## 一句话

**界面是看出来的。先花十分钟让它可见，比写完后推倒重来便宜得多。**
